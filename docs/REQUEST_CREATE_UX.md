# DAN 요청 작성 UX

최종 원칙: **사용자는 요청을 빠르게 올릴 수 있어야 한다.**

AI가 계속 질문하거나 긴 대화형 위저드를 거치게 하지 않는다.
요청 종류별로 **거래에 꼭 필요한 핵심 정보만** 구조화해서 받는다.

> **짧은 구조화 폼 + 2단계 이내 + 나머지는 자유롭게**

## Non-goals (지금 단계)

| 하지 않음 | 하는 것 |
| --- | --- |
| AI 자동 문장 재작성 | 기본 필수 필드 검사 |
| 대화형 추가 질문 | 보상·가격·시간·위치를 **별도 필드**로 수신 |
| 복잡한 요청 품질 평가 | BUY / SERVICE를 비슷한 UX 문법으로 유지 |

이상하게 쓴 제목(`BX잘사람`)을 DAN이 억지로 고치지 않는다.
응답률 저하는 작성자 책임으로 둔다.

## 플로우

```text
홈 → 요청 종류 선택
  → 1. 무엇을 (핵심 거래조건)
  → 2. 어디서 · 언제
  → 게시
```

### BUY — 1. 무엇을

- 찾는 제품 — 필수
- 희망 가격 — 필수
- 상태 — 선택

### BUY — 2. 어디서 · 언제

- 거래 방식 (택배 / 직거래)
- 직거래 시 지역 — 선택적
- BUY는 택배 가능 → **현재 위치가 필수는 아님**

### SERVICE — 1. 무엇을

- 부탁할 일 — 필수
- 보상 — 필수
- 예상 소요시간 — 선택
- 추가 설명 — 선택

### SERVICE — 2. 어디서 · 언제

- 위치 — 필수 (**현재 위치 사용** 또는 **장소·지역 검색** 중 하나)
- 날짜/시간 — 필수
- 상세 장소 설명 — 선택

위치 **권한 강제 아님**. 둘 중 하나만 만족하면 게시 가능.

## 위치 프라이버시

```text
사용자 현재 위치
  → 내부 좌표 저장 (Place.geo)
  → 거리 계산 / 주변 매칭 (향후)
  → 공개 화면: 대략 지역만 (예: 평택시 · 부대 근처)
```

- GPS 좌표·정확한 주소를 피드/상세에 노출하지 않음
- 정확한 만남 장소는 연결 후 채팅에서 정함

## 상세 페이지

큰 구조 유지. 마케팅 리드(`필요한 사람이 먼저…`)는 넣지 않음.
정보 중심 + 역할별 CTA:

- 소유자: `[수정] [요청 마감]`
- 다른 사용자: `[제가 할게요]` (BUY는 보유/판매 경로)

## 제품 포지션

DAN은 **AI가 요청을 대신 작성하는 서비스가 아니라**,
필요한 사람이 **조건을 빠르게 걸고 수요를 남기는** 서비스다.
위치·가격·보상·시간처럼 매칭에 필요한 데이터만 확실하게 구조화한다.
